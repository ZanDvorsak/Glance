# Fix: video frames, resize restarts and silent ffmpeg exits (review M9)

Branch `claude/fix-video-frames-758f1a`, based on `main` at 8d2d13c (runner-service architecture + the renderer-memory fix).
Finding: **M9** in `docs/reviews/review-full-codebase.md`, plus its two nits (a silent ffmpeg exit shows "Loading video..."
forever; `_cts` is never disposed).

## 1. Re-assessment on the current `main`

Where video runs now (`docs/design/runner-service.md` section 5): ffmpeg is started only by the user's own processes, the tray app
(`DisplayPusher`'s render loop thread) and the editor (preview on a 66 ms `DispatcherTimer`, i.e. the UI thread, `MainWindow.cs:144`;
also the virtual display window), always as the user. The service never decodes video. So the redesign moved *where* M9 happens, it
did not remove any of it: the tray app is the process that runs for days, and the editor preview is the one that resizes.

The renderer-memory fix (M10/M11, `docs/reviews/review-renderer-memory.md`) added a file stamp to video entries (L4: a replaced video
file restarts). It did not touch `VideoSource`, the cache key (`path|WxH|fit`) or the sweep (3 s), so it removed nothing from M9 either.

## 3. What changed

### `VideoSource` (`src/Glance.Core/Media/VideoSource.cs`)
- **Nothing slow on the caller's thread.** The constructor only computes the size and starts a background thread ("Glance video
  decoder"). That thread runs `Ffmpeg.Find`, starts ffmpeg and reads frames. `FfmpegMissing`, `Stopped` and `Error` are set from there.
  The read loop used to block a thread-pool thread for the life of every video; now it has its own thread.
- **Reference-counted frames.** Each decoded frame is a `Frame` with a count: one for the source while it is the newest, one per
  borrower. `AcquireFrame()` returns a `VideoFrameLease` (taken under the source's lock, so the source cannot drop its reference in
  between); the image stays valid until the lease is disposed, even if newer frames arrive. A frame is disposed the moment it is neither
  newest nor borrowed. `Dispose()` releases the newest frame and stops ffmpeg; a frame that arrives after `Dispose` is freed at once.
  The unsafe public `Latest` property is gone. `LiveFrames` (internal) counts frames not yet freed.
- **Dispose during start-up.** Disposed while ffmpeg is being looked for: it is never started. Disposed while `Process.Start` runs:
  the process is killed and disposed as soon as it exists.
- **Silent exit.** When ffmpeg's output ends and we did not stop it, the source waits up to 2 s for the exit code and sets `Stopped`
  with `Error` = the last stderr line, or "FFmpeg stopped without a message (exit code N); trying again shortly". A failed start sets
  `Stopped` with the exception message.
- `_cts` is gone (the lock-guarded `_disposed` flag replaces it), so there is nothing left undisposed.
- **FFmpeg rules intact.** The executable still comes only from `Ffmpeg.Find` (with its `FolderTrust` rule for elevated callers);
  `FfmpegProcess.Start` passes every argument through `ProcessStartInfo.ArgumentList`; the argument list is unchanged (`Arguments()`).

### `FfmpegProcess` / `IVideoProcess` (`src/Glance.Core/Media/VideoProcess.cs`)
The child process as the source sees it (output stream, wait for exit, exit code, kill). The real one waits for the last stderr lines
after exit so a final error message is not lost.

### `ThemeRenderer` (`src/Glance.Core/Themes/ThemeRenderer.cs`)
- `DrawImage` borrows the video frame with a lease and disposes it after the draw.
- `GetVideoFrame`: if a decoder for exactly this size and fit exists, use it. If not, and another decoder of the same file exists
  (another size or fit, most recently used), the new size must be asked for without a gap of more than `VideoSizeGapMs` (1 s) for
  `VideoSettleMs` (500 ms) before its decoder is created; meanwhile the other decoder's frames are stretched to the new box. They are
  also shown while the new decoder has no frame yet, so a resize never flashes "Loading video...". A file with no decoder at all starts
  at once (opening a theme does not wait). Pending sizes are forgotten by the sweep after 1 s.
- A decoder that `Stopped` is retried after `VideoRetryMs` (5 s), like a missing FFmpeg; not every frame.

## 4. Not covered / for the user to check

Things the tests cannot see (they need the real app, real videos, or a long run):

1. **A video background plays** in the editor preview, the virtual display and on the display (tray app), at the usual speed.
2. **Resize a video widget by dragging its handle**: the video keeps playing (stretched) during the drag; about half a second after you
   stop, it switches to a sharp decode at the new size without a "Loading video..." flash. Task Manager shows one or two `ffmpeg.exe`
   processes, not dozens; the extra one disappears about 3 s after the switch.
3. **Memory over a few minutes**: with a full-screen video playing, the tray app's (and the editor's) private bytes in Task Manager stay
   flat instead of climbing (on `main` they grow until the finalizer catches up; ~9 MB/s at 15 fps in the worst case).
4. **A broken video** (rename a text file to `.mp4`): the widget shows ffmpeg's error, and it is tried again every ~5 s (one short-lived
   `ffmpeg.exe` each time).
5. Ending ffmpeg by hand in Task Manager while a video plays: the widget keeps its last frame and the video comes back within ~5 s.

Known limits, unchanged: `Dispose` still kills ffmpeg on the calling thread (the editor's UI thread when a video is swept; now rare,
since a resize no longer creates a source per size). Frames are still allocated per frame (`SKImage.FromPixelCopy`), but freed at once.
