# Review: video frames, resize restarts and silent ffmpeg exits (M9)

- **Verdict:** merge. Frame lifetime, dispose ordering, the resize debounce and the restart are correct in every case I traced; the items below are optional follow-ups
- **Build/tests:** build 0 errors (`-p:SkipHost=true`); 806/806, three runs in a row (~16 s each). The real-ffmpeg test ran (FFmpeg is installed here) on the clip it generates itself, not on user media. I did not run the editor, the tray app or the service
- **Proof:**
  - Before: at `0b69dcf` (seam + tests, `main` behaviour) 7 of 11 `VideoFrameTests` fail as claimed: replaced frame not disposed; held frame never freed; 168/168 frames never disposed (the author saw 288; the count depends on timing); `Expected: 1, Actual: 51` ffmpeg starts for a 50-step drag; launch thread = render thread; silent exit leaves `Error` null; a stopped ffmpeg is never restarted. The 4 guards pass
  - Before: the seam changes no behaviour: the rest of the suite passes at `0b69dcf` (791/791), and by reading the diff the arguments, `ArgumentList`, stderr handling and Kill/Dispose are the same (only a `null` from `Process.Start` now becomes an error instead of a `NullReferenceException`)
  - After: all 15 video tests pass, 806/806. My own mutation checks: removing `|| v.Stopped` from the retry fails `M9_a_video_whose_ffmpeg_stopped_is_started_again_later`; removing the `AddRef` in `AcquireFrame` crashes the test host (see L4)
  - Checked by reading the code: a lease is taken under the source's lock, so a frame is never freed while a drawer holds it; a frame published after `Dispose` is freed at once; ffmpeg is killed before its pipe is closed; `Ffmpeg.Find` (with `FolderTrust`) is still the only source of the exe; `Ffmpeg.Find` is locked and safe to call from several decoder threads
  - Merges: `git merge-tree` is clean against `claude/fix-tray-deadlock-a14e66`, `claude/fix-ui-thread-280814` and `claude/fix-sensor-feed-07b0e8` (the only shared file is `AGENTS.md`). The branch adds no `await`, `.Result` or `.Wait()`, so the tray-deadlock branch's `ConfigureAwaitGuardTests` is not affected

## Findings
- **Low L1** — The wait before a new size gets its own decoder restarts after any 1 s gap without a render (`ThemeRenderer.cs:442-448`). A renderer that draws less than once a second (the tray loop during USB back-off, a very slow full-screen render) never reaches 500 ms, so the widget keeps showing the old decoder's frames, stretched and soft, for as long as that lasts (no extra processes) → restart the wait only when another size of the same file was asked for in between, or scale the gap to the renderer's frame interval; add a test that renders every 1.2 s
- **Low L2** — `Dispose` still kills ffmpeg on the caller's thread (`VideoSource.cs:197-215`) with `Kill(true)` (`VideoProcess.cs:52`), which walks the whole process list. In the editor that runs on the UI thread when the old decoder is swept after a resize, on every retry and when a theme closes → hand `StopProcess` to the pool or to the decoder thread, and use `Kill()` (ffmpeg starts no child processes)
- **Low L3** — A file that is always broken is retried every 5 s forever, one short-lived ffmpeg each time, without a log line (`ThemeRenderer.cs:466`). This is no spawn storm, but it never stops → double the wait per failure up to about 60 s, reset it after a run that produced frames, and log the error once
- **Low L4 (tests)** — Drawing a freed frame shows up as a native crash that aborts the whole test run ("Test Run Aborted"), not as one named failing test (my mutation: no `AddRef` in `AcquireFrame`) → in `M9_frames_decoded_while_another_thread_draws_are_all_disposed` (`VideoFrameTests.cs:178`) assert `img.Handle != IntPtr.Zero` before `DrawImage`
- Nits: the fallback decoder can belong to another widget with a different fit, so for about 0.5 s a Cover or Contain frame is stretched into the box (`ThemeRenderer.cs:432`); `FfmpegProcess.WaitForExit` then calls `WaitForExit()` with no time limit (it waits for stderr to close; fine for ffmpeg) (`VideoProcess.cs:46`); the resize wait uses `Now()` but `LastUsedTicks` and the 3 s sweep use `Environment.TickCount64`, so tests cannot drive the sweep; every frame still allocates a new native image (freed at once now; a small buffer pool would avoid it); the "nothing happened" checks wait with `Thread.Sleep` (they can only pass by mistake, never fail by mistake); `With_real_ffmpeg_...` reports a pass when FFmpeg is missing (on CI)

## Manual checks for the user
- A video background plays at normal speed in the editor preview, in the virtual display and on the LCD through the tray app
- Drag-resize a video widget: it keeps playing (stretched) during the drag and turns sharp about 0.5 s after you let go, with no "Loading video..." flash. Task Manager shows one or two `ffmpeg.exe`, never dozens, and the extra one is gone about 3 s later
- Leave a full-screen video playing for 5 minutes: private bytes of the tray app and the editor stay flat in Task Manager
- Rename a text file to `.mp4` and use it: the widget shows ffmpeg's error, with one short `ffmpeg.exe` about every 5 s. End `ffmpeg.exe` in Task Manager while a good video plays: the last frame stays and playback resumes within about 5 s
- Close the theme or the editor while a video plays: no `ffmpeg.exe` is left running and the window does not hang
