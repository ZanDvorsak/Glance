## Findings
- **M1** — Merging with M7 (`claude/fix-ui-thread-280814`) breaks the build and the guard. M7 adds `Core/Themes/ThemeSaveJob.cs:81` (`await Task.Run(job.Run); job.Apply();`), which needs to come back on the UI context on purpose. CA2007 rejects that line, and the guard has no escape hatch (`ConfigureAwaitGuardTests.cs:35` also flags `ConfigureAwait(true)`). `git merge-tree` also reports conflicts in `RunnerContext.cs` and `AGENTS.md`, and an add/add conflict in `UiThreadAuditTests.cs`, where both branches define class `UiThreadAuditTests`. → Move `SaveAsync` (the await and `Apply`) into `Glance.App`, or give the guard an explicit marker comment. Rename one test class. Merge `UiLikeContext` and M7's `TestUiThread`. Choose one off-UI design for the tray: M7's `SerialWork` worker makes `BackgroundOpener` unnecessary. Keep this branch's checks in `Opened` (power, pause, pusher already open).
- **M2** — Merging with M5 (`claude/fix-live-lease-pipes-4301b2`): its new `Core/Control/TrayControlServer.cs:58,68,88,92` awaits without `ConfigureAwait(false)`, so the build fails after the merge. Its `TrayLink.cs:61` blocks with `SendAsync(..).GetAwaiter().GetResult()` and no timeout. Its `RunnerContext` still calls `Supervise()` before `StartControlServer()`, which is the 0.2.0 order. `RunnerContext.cs` conflicts. → Add `ConfigureAwait(false)` there. Give `TrayLink.Send` a timeout. When resolving the conflict, start the control server before the first `Supervise()`.
- **L1** — `Opened` (`RunnerContext.cs:249-251`) stops an unwanted pusher while it holds `_gate`, with `StopTimeout` (18 s), on a pool thread. Meanwhile the UI's 2 s `Supervise` tick and the editor's NEXT/PAGE/BRIGHTNESS/LIVE (`Execute`, `:467-490`) wait on `_gate`, and LIVE gives up after 5 s. This happens when you pause during an open and the transfer stalls. → Hand the pusher over under the lock, call `Stop` outside it, then `RememberClosing` under the lock.
- **L2** — `Quit` (`RunnerContext.cs:507-526`) does not wait for an open that is still running in the background. The process can exit after the new pusher has drawn a frame (USB without the service) and before `Opened` blanks it, and `Opened` then uses the `_sensors` that `Quit` has already disposed. → In `Quit`, wait for `!_opener.IsOpening` with a limit (`QuickStopTimeout`), or give `BackgroundOpener` a bounded `WaitIdle`.
- **L3** — The tray's actual fix (new constructor order, `BackgroundOpener` wiring, `Opened` decisions) has no test. Moving `Supervise()` back above `Task.Run(ControlLoop)`, or opening on the UI thread again, would pass all 819 tests. The guard only checks `await`, not the rule "never block without a timeout", so M5's `TrayLink.Send` would get through. → Move the startup and `Opened` policy into Core and test it on `UiLikeContext`. Extend the scan to `.Result`, `.Wait()` and `GetResult()` with an allowlist marker.
- **L4** — The UI thread still blocks for a bounded time; this is the author's own follow-up. The tray calls `PayOwedBlank` → `DisplayConnector.TryBlank()` (`:330`) and `DisposePusher(StopTimeout)` under `_gate`. The editor calls `TryOpen` and `Release` (`MainWindow.cs:1447,1510,1519`). Against a hung service, each request can take up to 0.5 s + 10 s + 2 s. → M7 fixes this; make sure it merges.
- **Nits:** `PinnedPage` is set after the loop has started (`:255`), so the first frame can show the wrong page; pass it into the open lambda. A posted `Supervise` usually still sees `IsOpening` because the flag is reset after `done`, so a failed open is retried on the next tick, not at once. A `Reload` during an open keeps the pusher made before the reload. `Task.Wait` on an STA thread still pumps COM messages (unchanged from before). `Exchange` starts one `Task.Run` per frame (negligible at 2.5 fps).

## Manual checks for the user
- Reinstall, then sign in or start the tray: your theme is on the display within a few seconds, and the tray menu shows "Showing ...", not "Opening the display..." for long.
- `C:\ProgramData\Glance\service.log` has "Display opened for session 1". `%AppData%\Glance\runner.log` has "Display opened through the Glance service" and no repeated "Could not open the display" lines.
- Exit the tray, then use the editor's Send to display: the theme appears and the editor stays responsive. Turning it off blanks the display.
- Restart the Glance service while the tray runs: the display comes back within about 10 s, and the logs show one reopen, not a flood.
- Stop the service and start the tray: the tray menu answers at once and the editor's Next page still works. Then sleep and wake once: the display goes black, then comes back.
